# Nullsec-1 Technical Report

**Nullsec-1.0** — a security-native LLM for AI-generated software.

This report documents what Nullsec-1 is, how it is trained and aligned, how it is evaluated, and where its current limits are. It is written to be honest about the state of the project: Nullsec-1 is an early but real security LLM, and this report distinguishes what works today from what is future work.

## 1. Motivation

Software is increasingly generated by language models and autonomous agents. The resulting code ships fast and frequently carries a recognizable class of security defects: hardcoded secrets, missing authentication on sensitive routes, unbounded wallet transactions, prompt-injectable agent loops, over-scoped MCP tools, and unpinned dependencies. General code models can describe these issues but are not built to enforce a standard, and their judgments are not safe to trust as a deployment gate.

Nullsec-1 is purpose-built for this setting: a security-native model whose verdicts are constrained by a deterministic safety layer that an agent cannot argue its way past.

## 2. Model

Nullsec-1 is **not trained from scratch.** It is a specialized security LLM fine-tuned from Qwen2.5-Coder-7B-Instruct (Apache 2.0), config-swappable to the 14B variant. Fine-tuning uses QLoRA: the base is loaded in 4-bit NF4 with double quantization, and low-rank adapters are trained on the attention and MLP projections. This keeps v1 trainable on a single 24GB GPU.

## 3. Training objective

Supervised fine-tuning with completion-only loss. Each training record is a chat sequence: a fixed system instruction defining the strict security-reviewer role, a user turn containing a file and its code, and an assistant turn containing the target verdict JSON. Loss is masked to the assistant completion (via the Qwen assistant marker), so Nullsec-1 is optimized to produce the verdict, not to reproduce the prompt.

Critically, **every training target is passed through the same Security Alignment and Safety Layers used at serving time** before it enters the corpus (`training/prepare_dataset.py`). Malformed or enforcement-inconsistent verdicts are dropped. The model is therefore never trained against a target that the deterministic layers would reject, which keeps the learned and deterministic halves of the system mutually consistent.

## 4. Security alignment

Alignment in Nullsec-1 is deterministic, not learned reward modeling. Two layers sit between the model and any trusted decision:

1. **Security Alignment Layer** — parses, schema-validates, type-checks, and severity-normalizes raw output.
2. **Nullsec Safety Layer** — enforces production-readiness via fixed rules (R1–R6), raises severity/risk to match findings, and computes the final `production_ready`.

This is the alignment philosophy of the project: a model's self-assessment is advisory, and safety is enforced by code that cannot be persuaded. See `docs/architecture/nullsec1_architecture.md`.

## 5. Taxonomy

Nullsec-1 classifies findings against a fixed 15-category taxonomy, each mapped to one of eight check dimensions (`auth, secrets, input_validation, rate_limits, permissions, dangerous_exec, dependency_risk, environment_exposure`). The taxonomy (`taxonomy/taxonomy.json`) carries default severities, CWE references, and detection signals, and is the single source of truth across training, enforcement, serving, and evaluation. Categories are chosen for the AI-generated-software threat surface, including prompt injection, MCP tool abuse, and wallet/smart-contract risk alongside the classical web vulnerabilities.

## 6. Benchmark methodology

The benchmark suite (`benchmarks/`) is built on one rule: **no invented numbers.** A benchmark report is produced only after obtaining real Nullsec-1 outputs for a labeled dataset, either by running the model live (`--mode model`) or by scoring captured real outputs (`--mode replay`). Datasets contain ground-truth labels only; the repository ships no precomputed result files. A case with no available output is scored as a real miss, never as a synthetic pass. Every report is stamped with provenance: model fingerprint, version, run mode, dataset, and timestamp.

Metric families:

- **Detection accuracy** — precision, recall, and F1 of findings against labeled categories.
- **False-safe rate** — the fraction of genuinely-unsafe cases that end up marked `production_ready` after the Safety Layer. This is the primary safety metric; the Safety Layer is designed to drive it to zero.
- **Hallucination rate** — the fraction of clean cases on which Nullsec-1 reports findings (invented issues).
- **OWASP coverage** — per-category detection recall against OWASP Top 10 (2021) and OWASP LLM Top 10 (2025) tags, and the fraction of represented categories detected.
- **Patch correctness** — structural correctness of generated patches: non-trivial, diff/code-shaped, and not reintroducing a known-insecure signal for the finding's category.
- **Secure generation score** — the fraction of generated patches free of known-insecure signal tokens from the taxonomy.

## 7. Limitations and future work

- **Dataset scale.** The initial seed dataset bootstraps training and validation. Production-grade detection requires substantially larger curated corpora from CVEs, scanner outputs, and real AI-generated application failures. The ingestion scripts (`nullsec/ingest/`) exist to build this; auto-ingested examples require curation of their patch and check fields before use as training targets.
- **Patch verification depth.** Patch correctness is currently structural. Compile-, run-, and test-based verification of generated patches in a sandbox is future work.
- **Coverage breadth.** Seed language coverage is concentrated (Python, JavaScript/TypeScript, Solidity); breadth across Go, Rust, Java, and PHP grows with the corpus.
- **Residual model error.** Deterministic enforcement bounds the worst case (an unsafe verdict with a detected finding cannot be marked production-ready), but it cannot detect a vulnerability the model never surfaced. A clean verdict reduces risk; it does not prove safety.

## 8. Reproducibility

Training is reproducible from `training/config.yaml` (seed, hyperparameters, LoRA configuration). Evaluation is reproducible from the benchmark runners and datasets. Release identity — including a SHA-256 fingerprint over the security-defining artifacts — is reported by `GET /v1/model` and `python -m nullsec.core.version`.
